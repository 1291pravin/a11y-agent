One-time setup · hands-off from here on

Ship a11y-clean releases without touching accessibility again.

Customer drops in a website URL + a repo once. The system analyzes the site, drafts journeys with real screenshots, gets human sign-off, runs the audit, and then loops autonomously: fix agents open PRs, a verifier spins a dev server and re-runs the journey locally, PRs merge, the system re-scans. Regressions get their own fix task. Weekly, forever.

01 What changes

The current app already covers onboarding, journey discovery, Cursor dispatch, and post-merge verification. This plan closes the loop and makes it truly hands-off.

Today

Discrete, human-triggered steps

  • Quick scan uses checkbox focus areas — Home, Menu, Cart, etc.
  • Journey proposals show step text only — no screenshots.
  • After accepting proposals, the user still has to click Run on each journey.
  • Fix dispatch is per cause, one at a time.
  • Post-merge verification hits the remote AQA suite only — no local proof.
  • Regressions require the user to re-dispatch manually.
  • Site analysis is limited to what the runner sees on a single page inspection.
After this plan

One-shot setup, continuous multi-agent loop

  • Free-form intent prompt replaces checkboxes: "we sell cosmetics in FR/EN, biggest a11y risk is checkout & the cookie banner".
  • An Analyst agent crawls the site broadly, builds a page taxonomy, cross-references the repo.
  • Proposed journeys include Playwright screenshots per step — visual approve/remove.
  • Approval automatically runs Evaluate across all approved journeys and delivers a report.
  • Fix All dispatches a bounded batch of agents in parallel (Cursor Cloud & CLI).
  • New Local Verifier service spins the dev server, re-runs the journey on the PR branch, and posts before/after screenshots to the PR.
  • Autopilot re-scans on schedule, auto-dispatches, learns from failed attempts, budgets itself.

◎
Analyst
Site & repo comprehension
Model: composer-2.5 (planning) · Kind: LLM + tools
Tools: HTTP crawler, Playwright inspect, repo scanner (existing mapper.mjs), sitemap.xml reader
  • Reads the customer prompt.
  • Crawls up to N pages (BFS, same-origin, budget-bound).
  • Detects framework (Next / Nuxt / Astro / Vue / plain), CSS system, i18n roots.
  • Emits a page taxonomy: Home / PDP / PLP / Cart / Checkout / Account / Legal / Localized twins.
  • Feeds Journey Designer + Fix Planner with repo tokens (class, data-testid, aria-label).
↦
Journey Designer
Turns intent + taxonomy into journeys
Model: composer-2.5 · Kind: LLM (structured JSON out)
Tools: journey step schema, focus prompt, dry-run validator
  • Produces 4–12 candidate journeys with goto / click / fill / hover / waitFor / snapshot steps.
  • Marks cookie-banner clicks optional:true.
  • Guarantees at least one snapshot per journey with a rulesetId.
  • Coordinator sends each to the Runner for dry-run + screenshots before showing to human.
▤
Report Composer
User-facing findings
Model: composer-2.5 · Kind: LLM (narrative on top of deterministic totals)
Tools: cause store, journey lastRun, prior deltas
  • Extends the existing markdown report with prose & prioritization.
  • Groups causes by impact area: Perceivable / Operable / Understandable / Robust.
  • Suggests dispatch order: severity × cross-page reach.
⚒
Fix Agents (fleet)
Actual code fixes → PR
Provider: Cursor Cloud (composer-2.5) or Cursor CLI (local) — same shape
Kind: Autonomous coding agents, budgeted by Coordinator
  • One agent per root cause.
  • Prompt now carries prior failed-attempt evidence (from previous verifier runs).
  • Concurrency capped per site (default 3) so the account doesn't burn budget in one shot.
  • Existing cloud→CLI fallback path is reused as-is.
◉
Local Verifier
New service — proves the fix works
Kind: Deterministic executor · Port: 4175
Tools: git, npm/pnpm, Playwright, AQA evaluate
  • Checks the PR branch out into a scratch worktree.
  • Runs the detected install & dev-server command (or explicit user config).
  • Health-checks the URL, re-runs the offending journey against localhost.
  • Posts a PR comment: before/after screenshots, cause delta, verdict.
  • On fail: writes evidence into the state store so the next Fix Agent sees it.
☰
Autopilot Coordinator
The state machine + safety rails
Kind: Deterministic · Node module in server/
Tools: scheduler, budgets, kill switch, activity feed
  • Owns every transition: analyzing → proposing → approved → scanning → fixing → verifying → merged → verified → regressed.
  • Weekly re-scan cadence (existing scheduler, extended).
  • Respects maxAgentsInFlight, maxPRsPerDay, maxRetriesPerCause.
  • Auto-pauses if 3 consecutive verifier fails on the same cause → escalates to human.

Where the LLM is not allowed

Nothing LLM-generated calls AQA, Cursor, or GitHub free-hand. The Analyst emits JSON that a deterministic function validates against a schema before any HTTP call. Fix Agents run in Cursor's sandbox, not ours. This preserves the existing design rule from PLAN.md: the model plans and triages; deterministic scripts execute.

New process — verifier/

Third process alongside server/ and runner/. Runs on port 4175 (loopback only). Owns:

  • A pool of scratch worktrees under data/verifier/<prNum>/.
  • A single-slot child-process manager for dev servers (start / health / kill).
  • Its own Playwright instance (isolated from the runner so the two don't fight over Chromium).
  • A tiny HTTP API: POST /verify, POST /kill, GET /health.

Kept separate because dev servers are heavyweight, sometimes hang, and eat memory. Killing the verifier process should never take the control plane or the journey runner down.

06 Roadmap

Six milestones. Each is independently deployable — you can stop after any of them and still have a better product than today.

M6

Free-form intent + streaming Analyst

1–2 days
Replace focus checkboxes with a textarea. Wire intent all the way through proposeWithLlm(). Add streaming crawler that emits partial pages to state.
  • UI: viewOnboardQuick() → textarea + optional dev-server block.
  • Backend: site.intent field, startAnalysis() in server/analyzer.mjs (new).
  • SSE endpoint /api/sites/:id/analysis/stream for the "analyzing" screen.
M7

Playwright screenshots in dry-run + review

2–3 days
Runner captures a screenshot at every snapshot step of every proposed journey. Stored as PNG under data/screenshots/. Proposal review screen shows the strip.
  • Runner: add page.screenshot() to journey-run.mjs after each snapshot.
  • Server: static route /screenshots/*, ACL by admin token when set.
  • UI: overhaul #/site/:id/proposed to the design in Screen 3.
M8

Approve → auto-scan → report

2 days
Accepting proposals runs Evaluate on all in parallel and drops the user on a new consolidated Report screen. Report Composer LLM adds narrative & prioritization.
  • API: POST /journeys/approve replaces /accept; queues runs.
  • UI: #/site/:id/report (design in Screen 4).
  • Report keeps its markdown export.
M9

Fix All batches + command center

3–4 days
Batch dispatcher with concurrency caps, budget guardrails, and a live command-center view. Prior-attempt evidence is threaded into re-dispatched prompts.
  • New entity fixRun.
  • Coordinator extends orchestrator.mjs with a scheduler loop for the fix run's lanes.
  • UI: #/site/:id/fix-runs/:id command center (Screen 5).
M10

Local Verifier service

4–5 days · biggest new bet
New verifier/ process. Checkout branch → npm ci → dev server → re-run the failing journey against localhost → post PR comment with before/after screenshots + delta.
  • Detect install/start from package.json when the user didn't fill them.
  • Isolate scratch worktrees with git worktree add.
  • Serve verifier evidence back to the control plane via PATCH /pr/:num/verifier.
  • UI: PR detail redesign (Screen 6).
M11

Autopilot: scheduler + kill switches

3 days
Extend existing weekly scheduler. Per-site autopilot policy. Regression detection auto-re-dispatches. Weekly summary emails. Kill switch on 3× verifier fail.
  • UI: #/site/:id/autopilot (Screen 7) + #/dashboard column (Screen 8).
  • New server/autopilot.mjs — thin scheduler over the coordinator.
M12

Cost, memory, weekly summary (polish)

2 days
Per-site cost accounting from Cursor usage fields. Persisted "attempt memory" for causes so Fix Agents learn across weeks. Weekly summary email via a webhook of the user's choice.

07 Risks & controls

This system spends money and opens PRs on your behalf. These are the ways it can go wrong, and how we contain each.

Runaway Cursor spend · HIGH
A "Fix All" on a site with 200 causes could burn hundreds of dollars.
Controls: per-batch soft budget in USD (default $6, configurable). Max PRs/day cap. Max agents in flight cap. All dispatches recorded to fixRun.spentUsd. Kill switch pauses batches instantly.
Fix agents pushing bad code · MEDIUM
A visual regression or broken behavior slipping into a merged PR.
Controls: Human merges by default. Local Verifier re-runs the journey against the PR branch before the PR is marked ready-to-merge, so a regression that breaks the flow blocks merge. Existing tests still run in CI. Autopilot never enables auto-merge without explicit opt-in.
Dev server won't start on the CI-like verifier host · MEDIUM
Needs env secrets, DB, or GPU. Detection fails.
Controls: user configures install/start explicitly (Screen 1). Env file support (never committed, copied into scratch worktree). Fallback: verifier reports "environment unavailable, falling back to remote AQA rescan" — same behaviour as today for that PR.
Journey Designer proposes wrong journeys · LOW
Misreads intent, picks blog article instead of checkout.
Controls: humans always approve proposals. Regeneration button per journey. Intent textarea persisted so re-analysis is cheap.
Fix loops forever on an unfixable cause · MEDIUM
Same cause reopens 5×; each attempt burns tokens.
Controls: maxRetries per cause (default 3). After that: escalate to human with prior attempt diffs attached. Autopilot pauses the whole site if 3 escalations pile up.
Verifier process leaks dev servers · LOW
Killed mid-run, orphaned Node processes eating RAM.
Controls: single-slot child process manager with pid tracking, verifier startup reaps orphans from data/verifier/*.pid, hard timeout on any single verify (default 5 min).
AQA rate limit trips under Fix All · LOW
Multiple parallel evaluate calls + verifier evaluate = burst.
Controls: existing sliding-window limiter in aqa.mjs already covers this. Verifier shares the same budget via process-level env. Configurable AQA_MAX_RPM.
Screenshots leak sensitive data · MEDIUM
Logged-in journey captures customer names, order numbers.
Controls: screenshots served only when admin token is set (or loopback). Optional redactSelectors: [".customer-name"] on journey — CSS-blur before capture. Retention default 30 days.

08 Decisions I need from you

Answering these unlocks building. Each has a sensible default; call out where you want something different.

1. Analyst crawl budget default
How aggressive should the initial crawl be? Default: 50 pages max, same-origin, depth 3. Alternatives: unlimited (slow), 20 (fast), or user-tunable per site.
2. Where does the verifier run?
Same host as runner/ is simplest. But if your team's dev machines can't spin dev servers cleanly, a dedicated Docker container per project (mounted repo) is safer. Default: same host, plain Node child process.
3. Auto-merge policy — off, opt-in, or per-site?
Auto-merge feels great but is scary. Default: OFF globally, per-site toggle available. Even when ON, requires: verifier ✓ + CI ✓ + no needs-human label + severity ≠ manual-review.
4. Analyst LLM cost — is composer-2.5 acceptable?
Analysis is a one-time expensive call. Default: composer-2.5, cached by URL hash for 7 days. Alternative: cheaper model for classify-only, keep composer-2.5 for journey design.
5. Screenshot storage & retention
Local filesystem is easy; S3 is cleaner for a fleet. Default: local data/screenshots/, 30-day retention. Alternative: pluggable, S3 supported.
6. How opinionated should Journey Designer be?
Two flavors: (a) propose 4–6 tight journeys aligned to intent (default), or (b) propose 10–15 covering every taxonomy bucket, user prunes. First is faster; second is more complete.
7. Autopilot summary — where does it go?
Email? Slack webhook? In-app only? Default: in-app "Weekly digest" screen + optional webhook URL per site.
8. Do we keep the "Full audit" path?
The current AQA-suite path stays valid for enterprise customers who already have suites. The plan above extends the Quick path. Default: both paths coexist; Full audit gets Autopilot for free once M11 lands.

09 Recap

If we build M6→M11 (roughly 15–18 working days), the product goes from "user drives every step" to "user drops in URL + repo + a sentence, approves 4 journeys once, then never comes back except to merge PRs". M12 removes even the merge step for teams that opt in.

The bet with the highest new surface is the Local Verifier — a whole new process that runs dev servers on the fleet host. If you'd rather stage it, we can ship M6–M9 first (already a huge UX leap) and defer M10 by a sprint.
